## Контекст

Команда OrchestrPay разрабатывает платформу обработки платежей с использованием Saga-оркестрации. Процесс включает взаимодействие между несколькими микросервисами: Payment Service, FraudCheck Service, Notification Service.

Возник архитектурный вопрос: где разместить логику оркестрации Saga - внутри одного из существующих доменных сервисов или создать отдельный сервис-оркестратор?

Это решение критически влияет на:
- Связанность между сервисами
- Сложность развертывания и масштабирования
- Ответственность за координацию процесса
- Возможности мониторинга и отладки

## Рассмотренные варианты

### Вариант №1 «Оркестрация внутри Payment Service»

Payment Service становится ответственным за координацию всего процесса обработки платежа. Внутри сервиса реализуется Saga-оркестратор, который управляет вызовами других сервисов.

Использование Camunda BPMN внутри Payment Service. Прямые HTTP/gRPC вызовы к другим сервисам. Хранение состояния Saga в базе данных Payment Service. Компенсационные транзакции реализованы как методы внутри сервиса.

### Вариант №2 «Отдельный сервис-оркестратор»

Создается специализированный Payment Orchestrator Service, который отвечает исключительно за координацию процесса обработки платежей.

Отдельный микросервис с Camunda BPMN. Независимая база данных для хранения состояний Saga. HTTP/gRPC клиенты для взаимодействия с доменными сервисами. Специализированные компенсационные операции.

## Сравнение альтернатив

| Вариант решения | Преимущества | Недостатки |
|-----------------|--------------|------------|
| Вариант №1 «Оркестрация внутри Payment Service» | - Простота развертывания (один сервис)<br>- Меньше сетевых вызовов<br>- Единая точка мониторинга<br>- Быстрая разработка MVP<br>- Меньше инфраструктурных компонентов | - Нарушение принципа единственной ответственности<br>- Сложность масштабирования<br>- Высокая связанность Payment Service с другими сервисами<br>- Сложность тестирования оркестрации<br>- Риск превращения в монолит |
| Вариант №2 «Отдельный сервис-оркестратор» | - Четкое разделение ответственности<br>- Независимое масштабирование оркестрации<br>- Легкость тестирования<br>- Возможность переиспользования оркестратора<br>- Слабая связанность доменных сервисов<br>- Централизованное управление процессами | - Дополнительная сложность инфраструктуры<br>- Больше сетевых вызовов<br>- Необходимость управления еще одним сервисом<br>- Потенциальная точка отказа<br>- Увеличение времени разработки |

## Принятое решение

Вариант №2 «Отдельный сервис-оркестратор»

Принцип единственной ответственности: Payment Service должен заниматься только доменной логикой платежей, а не координацией между сервисами. Масштабируемость: Оркестрация может стать узким местом при высокой нагрузке. Отдельный сервис позволяет независимо масштабировать координацию и доменную логику. Тестируемость: Отдельный оркестратор легче тестировать изолированно. Эволюция архитектуры: В будущем могут появиться другие процессы, требующие оркестрации. Отдельный сервис можно переиспользовать. Соответствие микросервисной архитектуре: Каждый сервис имеет четкую ответственность.
